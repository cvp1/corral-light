# Bugs found running the EGM panel, 2026-10-25

Found while running a three-vendor design panel through `corral-light
consult` (record: `~/aios/reviews/2026-10-25-egm-integration-panel/`).
Branch `lane-auth-posture-fixes`.

## Fixed on this branch

### B1. A Grok login failure read "Claude login expired"
**Seen:** `consult ask --lane grok` on a logged-out Grok lane died with
`Claude login expired — click Sign in … (or run claude auth login there)
[session/new: … 'Authentication required' …]`. `doctor` said, correctly,
`Grok — not logged in — run: ~/.grok/bin/grok login`.

**Cause:** `Pane._dead` passed every lane's dead reason through
`claude_auth.explain`, and `claude_auth._AUTH_RE` matches vendor-neutral
strings (`-32000`, `Authentication required`, `not logged in`). The pane
was also tagged `dead_cause = "auth"`, so `auth_sweep` would try to
resume it on the next *Claude* sign-in.

**Fix:** lanes in `OWN_LOGIN_LANES` (codex, grok, gemini) get
`lane_auth_remedy`: the lane's own name and its own login command
(`grok_launcher.login_command` / `codex_launcher.login_command`), with the
vendor error kept in brackets. Their `dead_cause` stays `None`, so the
Claude sweep leaves them alone. Claude and unknown lanes behave as before.

**Test:** `test_claude_auth.ADeadLoginIsSurvived.test_another_vendors_login_failure_names_that_vendor`
(fails on master, passes here).

### B2. `consult lanes` and a live pane disagreed on Grok's posture
**Seen:** `consult lanes` listed grok `postureEnforced: false`. The Grok
pane opened by `consult ask` in the same session reported
`posture_enforced: true`.

**Cause:** `available_agents()` hard-coded
`bool(spec["posture_via_config_dir"])` in its grok and codex branches.
Every other branch, and the live pane, use `posture_enforceable(spec)`,
which knows that argv lanes (grok) realize a posture at spawn. The list
was the wrong side.

**Fix:** both branches call `posture_enforceable(spec)`. Codex is
unchanged (false); grok now lists true.

**Test:** `test_corral_light.PostureRidesTheAcpMode.test_the_lane_list_says_what_a_live_pane_says`
(fails on master, passes here).

## Fast follow-up (not fixed)

### F1. `consult lanes` can serve a stale "available"
**Seen:** `consult lanes` showed grok `ok`. Minutes later the ask died
logged out, and `doctor` (which computes live) said not logged in.

**Likely cause (unverified):** `/api/lanes` serves the availability
worker's cached answer (`Availability.read` returns the last result and
only schedules a recheck once it is older than `period`). If Grok's token
lapsed between the worker's pass and the ask, the list was stale.
`open_pane` trusts that list to refuse an unavailable lane.

**Suggested fix:** `/api/lanes` returns `checkedAt`; `consult` refuses (or
forces a recheck) when it is older than a few seconds before opening a
pane; `consult lanes --fresh` forces one. Or invalidate on any pane death
with an auth-shaped reason on that lane.

### F2. `consult ask` cannot fail fast on a permission card
**Seen while building `/panel`:** `wait_turn` notices `needs-you`, prints a
warning to stderr, and keeps waiting until the timeout (up to 2400 s). A
script that must never answer a card has to poll `/api/state` itself and
cancel the pane (what `~/aios/skills/panel/panel.py` does).

**Suggested fix:** `consult ask|fanout --on-card=wait|cancel` (default
`wait`, today's behaviour). `cancel` cancels and closes the pane, leaves
the card unanswered, and returns `{"violation": "permission card"}`.
Related: return the turn's `tool` / `permission_auto` event count in the
ask JSON, so callers need not re-read the pane.
