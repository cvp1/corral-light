# Proposal — one portable install for Corral Light (container-first)

Status: PROPOSAL, 2026-10-01. Nothing built. Author: mac-host session.

## TL;DR

Ship Corral Light as **one multi-arch OCI image** (linux/amd64 + linux/arm64)
that carries pinned Python, Node, both npm adapters, the agent CLIs, and a
pinned copy of AI-OS Seed. The host needs only a container runtime and a
~40-line `corral` shim. One `compose.yaml` replaces the launchd plist, the
systemd unit, `install_service.py`, the `spike/ npm install` step, and the
second clone of Seed.

**Catch, stated first:** a contained agent reaches only what is mounted. On
mac-host today, panes use host-only things (macOS Keychain secret broker,
launchctl, brew, the IC-7300 serial port, gh/ssh keys). So: container is the
default install for every new host and every non-the operator user; mac-host's power
seat keeps the native checkout as "dev mode" until Phase 3 bridges the host
reach it needs.

## What is messy today (measured 2026-10-01)

| Pain | Evidence |
|---|---|
| Python drift | No pin. Hub floor is 3.9 (`hub.py:44`); mac-host runs brew `python3` 3.14; Seed scripts need 3.10+ (memory: seed-scripts-need-py310). |
| Two service formats | `com.cvp1.corral-light.plist` + `corral-light.service` + `corral-light-watch.{service,timer}`, generated by `install_service.py`. |
| Hidden setup step | `spike/node_modules` gitignored; `doctor.py` exists largely to explain the missing `npm install`. Needs Node on host. |
| Per-lane installers | Antigravity via `install_antigravity_acp.py`, Grok CLI separately, claude native installer path quirks (`F-LB3`). |
| Two repos, two clones | README: install Seed into `~/aios`, then clone Corral Light. Versions are not pinned to each other. |
| Workspace path mismatch | README and `sessions.py:410` assume `~/aios`. On mac-host that folder does not exist; the workspace is `~/ai-os`. |
| Canonical-checkout footgun | memory: corral-light-runs-from-canonical-checkout — a worktree silently loses two lanes. |

## The shape

```
host                                   container  ghcr.io/cvp1/corral-light:<ver>
────                                   ─────────────────────────────────────────
corral (sh shim)  ── docker compose ─▶ hub.py  (Python 3.12, pinned digest)
                                       spike/node_modules (baked at build)
                                       claude, codex-acp, grok, antigravity CLIs
                                       /opt/aios-seed  (Seed @ pinned tag)
127.0.0.1:8098  ◀── port publish ───── :8098
Ollama (native, GPU) ◀─ host.docker.internal:11434
~/aios        ── bind, same path ───▶ ~/aios        (the workspace)
~/notes       ── bind, same path ───▶ ~/notes       (content root)
volume corral-state ────────────────▶ ~/.local/share/corral-light
volume corral-home  ────────────────▶ ~/.claude ~/.codex ~/.gemini ~/.grok (logins)
```

Decisions inside that picture:

- **Same absolute paths inside and out.** Mount `~/aios` at the host's own
  path so transcripts, attach-file paths and agent output read identically on
  both sides. The container user's `$HOME` is set to the host's `$HOME`.
- **Host UID.** Compose runs as `${UID}:${GID}` so files agents write into
  bind mounts are owned by the operator on Linux. Docker Desktop on macOS maps this
  already.
- **Loopback only.** Publish `127.0.0.1:8098:8098`. The pairing gate and
  WebAuthn origin stay exactly as today.
- **Ollama stays native.** Containers on macOS get no Metal GPU. The hub
  already takes `CORRAL_OLLAMA_URL`; point it at `host.docker.internal`
  (Linux adds `extra_hosts: host-gateway`).
- **Logins live in a named volume, not the host's.** On macOS Claude Code
  keeps credentials in the Keychain, which a Linux container cannot read. The
  container does its own one-time login (`corral login claude`, already built
  in `claude_login.py`) and keeps it in `corral-home`. Nothing goes in an env
  file.
- **Restart policy replaces launchd/systemd.** `restart: unless-stopped` plus
  a compose healthcheck. `install_service.py` and the four unit templates
  retire for container installs.

## Mount scope (added 2026-10-01, after the operator asked "mount ~ or ~/aios?")

One setting, `CORRAL_SCOPE`, picks what the agents can see.

| Scope | Mounts | For |
|---|---|---|
| `aios` (default) | `~/aios` and `~/notes`, plus extras named in `CORRAL_EXTRA_MOUNTS` | Novices, new hosts. The sandbox is the product. |
| `home` | all of `~`, plus the shadow volumes below | Power seats. Equivalent to native reach for anything that is a file. |

**`home` gives back:** repos, `~/notes`, memory and skills under `~/.claude`,
`~/.key` files, ssh key files. That covers most of the host-reach loss.

**`home` still cannot give back:** the macOS Keychain, which is a service and
not a file. That rules out the secret broker and any Keychain-backed
credential. It also cannot give back launchctl, brew, osascript, desktop
notifications or USB serial on macOS. On a Linux host, `home` is close to
full parity.

**`home` breaks things unless shadowed.** The host's `~` holds Mac binaries
the container must never run. These were found on mac-host:

- `~/.local/bin/claude` is a Mach-O arm64 binary.
- `~/.venvs/aios-seed/bin/python3` is Mach-O. Every hook in
  `~/ai-os/.claude/settings.json` calls it by absolute path. Inside a Linux
  container those hooks fail to execute. A failing PreToolUse hook does not
  block, so the memory-mesh write guard **fails open silently**. That is the
  worst outcome here and the main reason shadowing is mandatory.
- `spike/node_modules` holds `codex-darwin-arm64` and
  `claude-agent-sdk-darwin-arm64`.
- `~/.gemini/antigravity-acp` holds a per-platform Antigravity build.

The fix is container volumes mounted over those paths, at the same paths,
holding Linux builds: `~/.local/bin`, `~/.venvs/*`, `~/.gemini/antigravity-acp`,
and any `node_modules` the hub runs from. Nested mounts shadow the host copy
inside the container only. `doctor` must also run each workspace hook once
and refuse to start if any hook cannot execute.

**Logins under `home`.** A Linux Claude CLI writes a plaintext
`~/.claude/.credentials.json` into the host's home, which the Mac host never
uses. Feed `CLAUDE_CODE_OAUTH_TOKEN` from the vault at start instead
(`~/.key/claude_code_oauth_token.key` already exists), so no credential file
lands in `~`. Whether gh and ssh config work from Linux is unverified
[NEEDS VERIFICATION]. On macOS both can depend on the Keychain.

**`~/notes` is in the default (the operator, 2026-10-01).** The second brain is
assumed to live there, and Corral Light's search already defaults to it.
Three rules come with it:

- **Create it before mounting.** If `~/notes` is missing, `install.sh`
  creates it as the user. Docker on Linux would otherwise create the missing
  mount source as a root-owned folder.
- **Writes leave the machine.** On the fleet, `~/notes` is Syncthing-synced,
  so a container agent's write reaches every host. Running as the host UID
  keeps ownership right on Linux. Conflict files are Syncthing's normal
  handling and need nothing new.
- **Pin the hostname.** Inside a container, `hostname` returns the container
  ID. Fleet doctrine says to believe `hostname`, and the single-writer rule
  keys on it, so an agent could write the wrong `00 Meta/Fleet/<host>/`
  folder or refuse to work. Compose sets `hostname:` to the host's own name.

**Why `aios` stays the default.** Mounting `~` removes the sandbox entirely,
and 52 GB of home is a large blast radius to hand a paired browser. `aios`
plus named extras keeps the "safe for anyone" story. On mac-host that is
`~/ai-os` and `~/notes`, with `~/Github` as the one extra. Symlinks that point outside
the mounted set will dangle inside the container. `doctor` should list them.

## Seed: bundled, not cloned

- The image carries Seed at a pinned tag in `/opt/aios-seed`. One Corral
  Light release pins one Seed release; the pair is tested together in CI.
- `corral init` runs Seed's `install.py --target <workspace>` from inside the
  image if the workspace is empty, or `--into` an existing one.
  `corral update` pulls the new image, then runs `install.py --update` the
  same way. No second clone on any host.
- **What does NOT move into the container: Seed's scheduler.** It reconciles
  launchd/systemd by design and its jobs touch the host. It stays host-native.
  That is the one place a host still needs Python, and `uv` with a
  `.python-version` (3.12) removes the version guessing there.
- The workspace path becomes one config value (`CORRAL_WORKSPACE`, default
  `~/aios`) used for the mount and for `sessions.py`'s default directory —
  fixes the `~/aios` vs `~/ai-os` miss on mac-host.

## Install, as a user sees it

```
curl -fsSL https://<release-url>/install.sh | sh   # writes ~/.config/corral-light/compose.yaml, pulls, starts
corral pair ABC-123                                 # docker exec under the hood
corral login claude                                 # once per host
corral doctor
```

Same four lines on macOS and Linux. The shim is POSIX `sh`, so no
`/bin/bash` vs `/usr/bin/bash` shebang trap.

## Keeping lanes current

- In container mode, an adapter bump is an image rebuild, not an on-host
  swap of `spike/node_modules`.
- A scheduled CI job runs `lanes check`; on `behind`, it builds a candidate
  image, runs the `selftest_*.mjs` suite plus `doctor` and one real prompt per
  lane inside it, and only then tags. Same "proven before anything moves"
  contract as `lanes update`, moved off the host.
- `lanes update` stays for dev mode.

## Dev mode (mac-host today)

A `compose.dev.yaml` override bind-mounts the checkout over `/app`, so edits
are live without a rebuild. The native checkout + launchd path stays
supported on mac-host only until Phase 3.

## What we lose, honestly

1. **Host reach for agents.** Keychain-backed `~/ai-os/bin/secret`, launchctl,
   brew, rigctl/IC-7300 serial, gh and ssh keys, osascript, desktop
   notifications. For a new user this is a feature: a sandbox. For the operator's
   daily seat it is a regression.
2. **A VM on macOS.** Docker Desktop (29.6.2, linux/arm64 on mac-host) costs
   memory and must start at login for the hub to come back after reboot.
3. **A second Claude login per host** because of the Keychain.
4. **`watch` probing from outside.** A sidecar can probe the hub, but cannot
   raise a macOS desktop notification. It needs a push channel instead.

## Phases

| Phase | Work | Done when |
|---|---|---|
| 0 | Dockerfile + compose; run beside native on :8099 on mac-host | `doctor` shows the same lanes ok in container as native, and each lane answers one real prompt |
| 1 | Seed bundled + `corral init/update`; `install.sh`; multi-arch CI build | A fresh Linux host goes from nothing to `/status` answering with the four install lines |
| 2 | CI-driven lane bumps; health sidecar with push notifications | One adapter bump ships with zero on-host steps |
| 3 | Host-reach bridges: secret broker over a mounted unix socket; optional device passthrough on Linux | mac-host cuts over and retires the launchd plist |

**Falsifier for Phase 0:** any lane that passes `doctor` natively but fails in
the arm64 container. Grok CLI arm64 Linux availability is unverified

[NEEDS VERIFICATION].

## Decisions only the operator can make

1. **Publish the image publicly on GHCR, or keep it private?** Publishing is
   outward-facing. Private works for the fleet; public is what makes this the
   novice install.
2. **Is the contained sandbox the product default?** Recommended yes. It fits
   the "safe for anyone" mission and makes host reach an explicit opt-in.
